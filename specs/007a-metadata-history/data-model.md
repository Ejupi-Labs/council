# Data Model: Project Metadata History

**Status: implemented; accepted for the bounded offline metadata-history scope** (see
[acceptance.md](acceptance.md); this model is not itself acceptance evidence). It began as a
draft design for feature `007a-metadata-history`. This model follows [spec.md](spec.md) and defines proposed logical
records and invariants, not a schema migration or a claim that current records
already prove eligibility. The physical store, exact schema, limits, transport,
platform primitives and complete acceptance tests must be fixed by the feature
plan and independently reviewed before implementation. All history is private,
**incomplete observational history**; it is not a backup, evidence export,
restoration, task acceptance or source of live execution authority.

## Source eligibility and captured selection

**FieldEligibility** identifies an allowed dedicated source field, its owning
record type, value kind, Council-controlled origin and a controller-established
provenance basis. The allowlist is finite, versioned and fixed by the approved
design; its permitted kinds are Council-generated identities and relationships,
validated canonical revisions/counters and known state/phase enums, plus a
Council-generated capture timestamp. A syntactically valid string, an ID supplied
by a caller, or a field's location in Council storage is not proof of generated
origin. Eligibility must be determined before reading a value, without inspecting
excluded content or vendor authentication. Unknown, unprovable or corrupt source
fields are omitted with a safe fixed reason, or the capture fails as required by
the spec; no user assertion can convert them to eligible.

The trusted source is the Council-managed database at its established private v2
location held under its native owner lock. This is an explicit trusted-local-state
assumption, not a proven database-origin attestation: the current schema cannot
detect a database copied or tampered with by the same user. This slice provides no
foreign database or archive import. Provenance is a documented source-and-write-path
property within the assumed boundary, not a cryptographic claim about arbitrary
stored values. User-controlled inputs and caller-chosen IDs remain ineligible even
when stored in an otherwise trusted record.

Candidate current-store sources for design review include the dedicated project
identity; task identity, project relationship, current version, revision and
state revision; and attempt identity, task relationship, task version, revision
and validated phase. Graph identities/relationships and their dedicated revisions
may be included only when the same provenance and scoping rules are established.
These are **candidates**, not an unconditional allowlist: the plan must document
which accepted creation and migration paths guarantee each field is generated by
Council and which existing/new records those guarantees cover, without reading
opaque fields. Current column shape, ID syntax or a schema marker alone does not
prove that guarantee. Within the stated trusted-store boundary, a documented
Council-only generation invariant may establish eligibility; this is not proof
against copied or tampered databases. It does not establish the origin of a copied
database as a matter of fact. A useful ordinary populated project must nevertheless
yield genuinely eligible task/attempt relationships without a client-supplied
provenance claim.

Any displayed ordering is a project-local ordinal derived from the bounded selected
project's deterministic order. Global database sequence values are internal ordering
inputs only and are never returned or exported: their values or gaps can disclose
activity in other projects. The ordinal does not establish graph dependencies,
execution causation, acceptance or a cross-project ordering.

The source selection must read only authorized dedicated fields. It never fetches
or decodes an opaque whole record to extract a supposedly safe value, including
serialized `data`, free text, labels, paths, commands, prompts, user files,
provider output, artifact payloads, environment, vendor authentication, owner
tokens, legacy data or fields from another project. Artifact identifiers and byte
counts are excluded unless separately admitted by the reviewed allowlist and
provenance rules; artifact files are never opened. The user-chosen output path is
an operation input used only for publication, never a history field.

**CapturedSelection** binds the selected existing project, authoritative source
owner/epoch and exact eligible field/record classes, source membership and
relevant revisions, omission reason codes and bounded counts. The owner obtains
a coherent point-in-time view of the selected project and validates every included
relationship against that scope. A relation whose parent is unqualified, missing,
foreign or ambiguous is not invented or silently rebound. Any omitted category
or relationship is named by a fixed, safe reason; omitted values and private paths
are not echoed. Counts and page sizes have explicit limits, with overflow rejected
or visibly incomplete rather than truncated as a complete selection.

## Immutable snapshot and local inspection

**MetadataSnapshot** has a Council-generated snapshot ID, schema/profile version,
project identity, capture timestamp and boundary, immutable captured eligible
records and relationships, source/control revisions, included field categories,
explicit exclusions and reasons, and `incomplete_history` status. Its safe data
contains no selected output path, provider/user text or private physical identity.
Snapshot content and its scope cannot be refreshed in place. A changed selection
requires a new snapshot ID; the immutable result can be paged without changing its
source view or omitting entries between pages.

States distinguish an eligible empty inventory from source unavailable, conflict,
limit-exceeded and failed/incomplete capture. The result must not falsely claim
that the selected eligible field set was captured coherently if source membership
or relevant revisions changed during the boundary. The history's incompleteness
never becomes a claim of full project or evidence completeness. A historical phase
is a captured observation at the boundary, not proof of current process ownership,
completed cleanup, accepted result or permission to dispatch.

**SnapshotReceipt** binds a user request ID and exact operation fingerprint to
its snapshot ID, outcome and durable receipt. Same-ID changed-project or changed
selection conflicts. Exact replay returns the original receipt and recorded
snapshot or its current inspectable unresolved status without creating a second
snapshot. Snapshots are private Council records, not user-supplied archives;
local UI and CLI inspect the same authorized snapshot without importing any file,
opening artifact payloads, making model calls or changing live work.

## Export preview and immutable payload

**ExportPreview** binds a new preview ID/revision, the exact immutable snapshot
ID/profile/content revision, selected local destination, included and excluded
categories, capture/source authority, incomplete-history warning, expected absent
target and controller-captured destination-parent identity and relevant conflict
observations. The destination is user-visible private operation data, not a field
of the exported snapshot. A preview has no publication effect and does not itself
authorize or reserve the target. Destination/parent identity and safety facts are
controller observations, never trusted client-supplied proofs.

The execute request names its own request ID and the exact preview ID/revision.
Changed scope, selection or destination requires a new preview; the owner checks
current authority, immutable snapshot identity and all relevant captured
preconditions again at the physical boundary. Unrelated later activity is not
silently incorporated into the existing snapshot. Missing authority, invalidated
source/destination assumptions, unsafe links, an already existing output or a
changed parent cause explicit refusal/incompleteness; no overwrite or silent
selection refresh is authorized.

**HistoryPayload** is a versioned, bounded, machine-readable encoding of the
immutable safe snapshot, selected project identity, field categories, fixed
omission reason codes, recorded relationships and explicit incomplete status.
An integrity value may be computed only over these eligible output bytes and
indicates byte integrity, not credential safety or acceptance. The encoding
contains no paths, free text, excluded source values, private tokens, unsafe
identifiers from unqualified fields or second-project records. It is not an
archive input contract; no arbitrary file import is supported. The user-selected
output is private data, not anonymized and not implicitly released or included
in Git history or packaged artifacts.

## Operation, receipt and effect journal

**HistoryExportOperation** is a controller-owned durable record containing an
operation ID/revision, exact request ID and canonical fingerprint; preview and
snapshot identities/revisions; project scope; user-selected local destination in
private operation state; accepting owner generation; current state; blockers and
safe next action; and a reference to append-only effect observations. The
fingerprint binds operation, scope, snapshot, preview, exact selection and
destination. An identical retry returns its original receipt with the recorded
result or current unresolved state; different input under the same request ID
is a conflict. A retry never regenerates or republishes the output.

Operation state distinguishes preparation, ready, effect in progress, completed,
failed, incomplete and uncertain. `completed` means publication of the exact
safe payload was observed, its file flush succeeded and its directory-sync outcome
was explicitly recorded as succeeded or documented unavailable; it does
not change the payload's `incomplete_history` meaning. A timeout, interrupted
owner, committed-but-unacknowledged write or missing post-effect observation is
not proof of no publication. Keep known outcomes and per-effect uncertainty
inspectable and fence conflicting actions until independently resolved.

**PublicationEffect** binds the one final-file publication to its operation ID,
owner generation, effect ID, selected filename and ordered immutable permit and
observation records. After the durable, positively acknowledged permit, the owner
creates the final filename directly using one anchored, no-follow exclusive-create
operation in the held verified private export directory, and writes only through
the retained handle. There is no path-based staging, rename or replacement step.
An uncertain permit commit never authorizes the OS call. The effect journal cannot
be deleted, truncated, silently replaced, or assumed complete when malformed.
File/directory identity, ownership and observed durability are private controller
facts, revalidated through held native authority and never accepted from user
assertions. The plan must specify platform-specific containment, file and directory
sync limits and support, and must not claim database and filesystem effects are
one transaction. Trust in the Council-private namespace excludes hostile same-user
tampering; ordinary collisions and detected changes still fail closed.

A successful operation never authorizes a second OS effect on receipt replay.
If the final file was created but writing, verification, required file flush or acknowledgement
cannot be proven complete, report the actual incomplete or uncertain outcome, retain
the partial final file and block conflicting publication. Partial bytes may be visible;
never call them a successful export, or automatically delete or overwrite them to
make a retry appear successful. Council does not stage or commit the output to Git
or include it in release inputs; this is not a claim that the user's private home
cannot itself lie inside a repository.
A separately requested later export requires a new preview, request and current
explicit destination authority.

## Owner-mediated no-effect reconciliation

**ReconciliationDecision** is append-only and binds an exact operation, frozen
revision, request, owner generation, verified observations, decision and retained
blockers. It is not a user-supplied proof. A supported positive case may record
that Council performed **no authorized filesystem effect for that exact
operation**, only after the controller establishes all of the following:

1. Closed-world permit discipline covers final-file creation and every subsequent
   output write, and a trusted, complete append-only journal contains no permit for that exact
   operation. No effect-capable route can bypass the permit boundary; an uncertain
   commit is not permission to call the OS. A missing journal row alone, absent
   output file, user claim or elapsed time is not proof.
2. In serialized owner state the exact operation/revision is frozen against new
   permits. A controller admission barrier prevents newly admitted actors, and
   all earlier registered operation actors and effect-capable handles have
   returned or are proved terminated before the final decision. Untracked
   workers, live handles, drain timeout or an unrecorded fence cause keep the
   case unresolved. Existing 007 engine drains and clean-owner checks alone do
   not prove this for new history workers; the implementation must integrate and
   verify all such actors and effects.
3. The current owner and held lock/generation are verified while the freeze and
   drain barrier remain in force. A live current epoch is normally dirty. A
   cross-owner decision requires independently established old-owner exclusion,
   validated exact-operation journal/freeze facts and a gap-free clean begin/close
   chain with history-specific lifecycle checks. Missing owners or lock acquisition
   alone are insufficient. A dirty or untracked prior epoch leaves the operation
   unresolved and retains its independent owner incident and applicable fence; it
   cannot be silently cleared or relabelled clean.
4. A final serialized transaction rechecks the exact freeze, journal completeness,
   owner, request/revision and all relevant existing claims/incidents, appends
   the decision, and releases only this operation's independently safe blocker.
   Other blockers retain their fences. The freeze prevents later permits; any
   desired new publication needs a fresh preview and fresh request authority.

This decision cannot establish that a path is absent or unchanged, that another
process had no effects, or that a credential-bearing or unqualified object is
safe. A possible permit, unknown stage, partial effect or insufficient evidence
remains unresolved and fenced; neither inspection nor restart automatically
opens the gate or replays publication.

## Required invariants and verification

1. Original records, user edits, other projects, legacy state and vendor
   credentials remain untouched. Data produced by this slice cannot be used to
   import an archive, restore history, grant authority or claim FR-042 complete.
2. Scope, profile, included fields, exclusions, snapshot identity and incomplete
   status agree across capture, UI/CLI inspection and any successful export.
   Request and effect identities remain stable and bounded; no model call occurs.
3. Controlled tests exercise two populated projects, genuine ordinary generated
   relationships, access sentinels on excluded columns/payloads and credential
   paths, unknown source provenance, inconsistent/oversized selection and
   concurrent source changes without application-level access to excluded user
   content or vendor credential files. No claim is made that database storage pages
   cannot contain excluded bytes or that same-user tampering is detectable.
4. Test destination existence, changed parent/object identity, symlink and swap
   races, publication failure, all effect-permit/acknowledgement boundaries,
   actual owner restart, exact replay and conflicting request identity. Verify
   only the selected output is produced, never overwritten or silently repeated.
5. Test freeze versus permit in both orders, a delayed registered actor, drain
   failure, final-file creation and partial-write boundaries, journal corruption and uncertain
   permit commit, same-owner and broken cross-owner chains, and independent
   blockers. The positive no-effect decision is allowed only when every proof
   holds; absence, a user assertion or a clean unrelated epoch is insufficient.
