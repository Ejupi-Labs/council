# Draft Contract: Isolated Restored History

**Status: design draft.** This contract describes the intended inspection seam; it does not claim that restore, its data structures, or the routes below are implemented. Final wire names and finite limits are set during the feature plan. The unresolved payload eligibility policy remains a prerequisite for reading, copying, hashing or exposing selected content; this document does not establish that policy or satisfy RET-004 with a metadata-only or fixture-only import.

## Purpose and boundary

A user who has restored a qualifying complete backup into an explicitly selected, initially absent isolated destination can use the current authenticated Council owner, UI and CLI to inspect its available project history. The owner presents original source relationships, exact retained identities and eligible evidence as **historical, read-only observations**. It also presents omissions, unavailable material, incomplete exports and interrupted or uncertain ownership without treating those states as successful work.

Each successful restore creates a new opaque local `historyImportId`. The owner maintains a catalog entry binding that identity to the restore operation, source backup and manifest digest, exact destination root and physical identity, supported format, declared completeness, and any visible omissions or uncertainty. Historical source project, task, graph, node, attempt, artifact and request identities are always qualified by `historyImportId`. Two imports may retain the same source IDs as each other or as a live project without being merged or aliased.

The destination is an isolated history namespace, never a live Council state root or a project being silently merged. The catalog entry alone is not proof that the destination remains intact: the owner revalidates the exact recorded physical root and relevant manifest members before each applicable read. A missing, replaced, redirected, unsafe or corrupted destination produces an actionable unavailable or integrity error; it does not cause fallback to a same-named live record or another import.

## Owner and transport seam

The current authenticated owner exposes a dedicated read-only history namespace. Illustrative routes, subject to the final interface contract, are:

| Read | Illustrative route | Result |
| --- | --- | --- |
| List imports | `GET /api/v1/history/imports` | Bounded page of catalog entries, source identities, completeness and state. |
| Inspect import and project | `GET /api/v1/history/imports/{importId}` | Source project and import identities, captured scope, manifest, omissions, uncertainty and availability. |
| List or inspect historical tasks | `GET /api/v1/history/imports/{importId}/tasks[/{sourceTaskId}]` | Scoped task versions, original instructions if eligible and included, relationships, retained status and availability. |
| Inspect attempts and events | `GET /api/v1/history/imports/{importId}/tasks/{sourceTaskId}/attempts[/{sourceAttemptId}]` and event reads | Captured attempts and events belonging to that historical task, retaining original outcomes and uncertainty. |
| Inspect artifact metadata and eligible bytes | `GET /api/v1/history/imports/{importId}/artifacts/{sourceArtifactId}` and `/bytes` | Exact manifest-bound historical metadata and bounded verified bytes, or an explicit excluded, unavailable or corrupt result. |

The implementation adds dedicated routing to `internal/httpapi/server.go`, a dedicated owner-backed application read seam through `internal/app`, and strictly validated import-scoped readers. It must use the existing owner authentication and lifecycle controls. CLI commands use the same owner APIs and identifiers through `internal/cli`; the UI adds a separately labelled History navigation and inspection controller. UI and CLI expose the same logical identities, results, completeness and errors. All list pagination is bounded and cursor scope includes the import identity and selected parent; invalid, stale, cross-import or forged cursors fail closed.

The existing `/projects`, `/tasks`, `/attempts`, `/artifacts`, graph, workflow and recovery endpoints remain live-authority namespaces. Current task reads in `internal/engine/observe.go` enrich attempts using current live owner state; the history reader must not call that enrichment on archived attempts. Existing workspace and task controllers select live records and offer mutations (`ui/src/workspace.ts`, `ui/src/tasks.ts`); a separate history view does not install an imported task as a live selection. History-specific DTOs represent historical states and identities explicitly rather than passing archived records as executable live task objects.

History routes expose reads only. Requests to start, adopt, resume, pause, accept, integrate, reconcile, mutate guidance, amend a budget or clean up through a historical route are rejected before effects; the UI presents no such controls in historical context. A later feature may define a separate, explicit creation flow from user-selected history, but this feature grants no such authority.

## Storage, reads and authority isolation

The restore operation validates the complete archive, format, references, eligibility, exact destination and collisions before effects, then rechecks them at each relevant filesystem boundary. It publishes only the explicitly reviewed destination and records the actual durable outcome. The owner's live catalog contains the minimum metadata needed to locate and validate the imported namespace; imported project/task/attempt records, audit items and bytes are not inserted into live operational tables merely to make them visible. Partial or uncertain restore effects remain separately inspectable and fenced; they are never registered as a verified complete import.

The existing `internal/store/store.go:Open` configures a writable database and may migrate it. It must not be used to open imported database bytes as the history-reader implementation. The design may use a versioned, constrained and validated restored representation or a separately implemented read-only adapter, provided it cannot migrate, attach as live state, run triggers or execute imported code, and its scope and content eligibility are established before access. Readers never trust archive-provided absolute paths, private runtime references or physical identities as current authority.

`internal/evidence` validates live-owned files against live store metadata and the current private root. Imported artifact bytes require a distinct import-scoped reader: resolve only an exact declared regular-file member beneath the validated restored root; reject links, aliases, duplicates, traversal, unknown members and scope mismatches; verify opened object and parent identity, size and digest using bounded reads; and establish payload eligibility before opening, hashing or displaying bytes. A prior successful validation does not replace the boundary check for a later read. Missing, incomplete or ineligible content remains visibly unavailable rather than being silently substituted with a live artifact sharing its source ID.

Historical receipts, owner epochs, descriptor tokens, process identities, claims, pause checkpoints, pending work and effect journals may be displayed only when included and eligible as inert history. They are never imported into the live receipt table or consulted by `Store.Replay`, and they do not authorize owner handoff, process termination, new dispatch, filesystem mutation or fence clearance. A historical outcome preserves its original uncertainty and primary failure. No restored process or writer is launched and inspection makes zero model calls.

No import-specific route accepts a live resource ID as a substitute for the exact historical namespace. A source ID may nevertheless be textually identical to a live ID: live endpoints continue to operate only on their own live records under their normal explicit authority. The UI must never construct a live mutation from a history selection, and no history request or archived receipt may supply or satisfy live mutation authority. This distinction does not prohibit a separately authorized, explicit live operation merely because an unrelated historical source ID has the same text.

## Required verification

Acceptance uses fake agents and isolated local roots; a real-use qualifying production backup/restore path remains a separate mandatory requirement. Tests must cover at least:

1. Restore a qualifying complete backup of one project beside an unrelated populated project. After owner restart, traverse import → project → task/version → attempt/event → eligible artifact bytes through both UI and CLI. Assert the same captured source identities and relationships, original outcome and exact included bytes, clear read-only labels, zero model calls, no restored writer and unchanged unrelated/live state.
2. Restore two independent imports containing the same source IDs, including IDs coinciding with a live task, attempt and request. Each import shows only its own manifest-bound objects. Historical routes reject all mutation methods; no UI action or historical receipt causes `Store.Replay` to return a live receipt, mutate a live task, launch an attempt or consume a budget. Independently authorized live actions retain their normal semantics.
3. Attempt cross-import parent/child lookups, unknown IDs, forged or cross-scope cursors, source-ID fallback and archive path traversal, duplicate names, links, hard links, special objects and excessive sizes. Reject each unsafe or ambiguous request without revealing unrelated records or changing any destination.
4. Replace or alter the restored root, a parent directory or an artifact after validation; remove or corrupt a referenced member; make an eligibility decision unavailable; and race a read with these changes. Return a truthful integrity, missing or excluded state without reading ineligible bytes or falling back to a live file. Compare destination and live state before and after rejected reads.
5. Interrupt restore after a durable intent and at each publication boundary; restart the owner and retry the exact request. Show known partial or uncertain effects and any applicable fence, preserve unrelated and pre-existing paths, and never repeat an effect or register a complete import without its verified closure.
6. Exercise an explicitly incomplete history projection and a record with unresolved process/effect ownership. Both remain labelled as such after restart; neither can clear a live incident, reactivate a receipt, acquire a live claim or become a complete backup through inspection.
7. Delay import/list/detail responses while the user changes the active live project, history selection or draft. A stale response cannot replace newer state, create a live mutation target or change the selected import.

The production-use scenario must demonstrate that qualifying source material acquired trustworthy credential-safe provenance in ordinary use, as required by RET-003 and RET-004. If that proof remains unresolved, expose the limitation and leave complete-backup acceptance open.
