# Council functional requirements

Status: draft for product review. These requirements describe the rebuilt product, independently of implementation language, framework, storage engine or the legacy Council architecture. Stable identifiers are intended for traceability into feature specifications, plans, tasks and acceptance evidence.

Council helps programmers deliver development tasks through their existing AI harnesses and provider accounts. Its primary value is choosing a suitably capable, economical execution target, using otherwise idle subscription capacity, and carrying work through the necessary implementation, review, verification and integration with little manual coordination.

“Must” identifies required first-release behavior. An acceptance example describes an observable result, not a mandated implementation or exhaustive test suite. The requested autonomous full-access policy is the primary execution experience; legacy read-only defaults, mandatory voting and a blanket prohibition on automatic integration are not new-product requirements.

## Terms and boundaries

| Term | Meaning |
| --- | --- |
| Provider | The organization or service supplying model execution. |
| Account | The explicitly identified subscription, API billing or local execution entitlement used by a target. Multiple targets can share one account. |
| Harness | The installed agent environment used to execute work, such as Codex, Claude Code, DeepSeek Harness, Junie or Antigravity. |
| Model | The requested or reported model identity within an execution target. A harness name or plan label is not a model identity. |
| Execution target | A configured combination of harness, account, model selection and supported capabilities. Unresolved native defaults remain explicitly unresolved. |
| Task | The requested development outcome, its original constraints, acceptance criteria, destination and execution policy. |
| Attempt | One execution of some task work, with a stable identity, selected settings, state and evidence. A replacement attempt does not erase the prior one. |
| Acceptance | A conclusion supported by the task's required checks and review evidence. A returned agent response or successful process exit does not establish acceptance. |
| Integration | Applying the verified result to the destination agreed for the task. Integration is distinct from generating a patch, committing locally or publishing externally. |
| Availability observation | A dated, sourced statement about occupancy or allowance. It is distinct from Council's own knowledge of work it has scheduled. |

## 1. Open a project and connect existing agents

| ID | Requirement | Observable acceptance |
| --- | --- | --- |
| FR-001 | The programmer must be able to open an existing project and reach a usable task composer without preparing transport configuration files. Advanced settings must not be required for the default journey. | On a fresh supported installation, a project with spaces and Unicode in its path opens, the selected project is visible, and a task can be prepared through the interface. Missing prerequisites produce specific setup guidance rather than a generic execution failure. |
| FR-002 | Council must discover or let the user select installed harnesses and report installation, connection and relevant capability status separately. A discovery check must not imply that authentication, model access or tool execution has been verified. | An installed but unauthenticated harness is not shown as ready for a verified live task. A target without a connection test is labelled unverified or unknown. Discovery makes no model call and does not start login. |
| FR-003 | Onboarding must reuse the user's existing harness authentication without reading, copying or rewriting vendor credential material or changing global vendor settings. Required login or installation steps must use the supported user-facing path. | Connecting an already authenticated harness leaves its account files and global configuration unchanged. Missing login is explained and does not cause credential import, hidden login or an unrequested agent installation. |
| FR-004 | Configuration and recorded execution must keep provider, account, harness and model identities distinct. Shared account links must be explicit. | Two model targets using one subscription show one shared account capacity source. Two accounts using the same harness remain separate. A plan label never appears as proof of the model used. |
| FR-005 | The first release must implement Codex, Claude Code, DeepSeek Harness, Junie and Antigravity adapters for the core task lifecycle. Optional capabilities and version-specific limitations must be reported per adapter. | Each adapter is exercised through controlled task execution, result/error handling, cancellation and retained evidence tests. A missing optional structured-output or inspection capability is disclosed before selecting an incompatible stage. Fake protocol coverage and authorized live qualification are reported separately. |
| FR-006 | Project collaboration data must remain outside Git history and distributable release artifacts. Council must provide a documented project-data location and identify what it stores there. | A project task, account observation and result history do not appear in a normal source commit or built release archive. Setup explains local stored content; the release test verifies that fixture state and credentials are absent. |

## 2. Describe the task and authorize work once

| ID | Requirement | Observable acceptance |
| --- | --- | --- |
| FR-007 | The primary composer must require only a project and task to begin, with `Auto` defaults for ordinary execution choices. Acceptance criteria, destination, model/account pins and advanced controls must be discoverable without being mandatory fields. | A programmer can submit a small, clear coding task without selecting a collaboration mode, choosing voting members or editing JSON. The admitted task records the resolved defaults and any explicit choices. |
| FR-008 | Council must preserve the original task, constraints and explicit choices losslessly, separately from generated plans, summaries and revisions. New guidance must be versioned and attributable. | After an agent produces a summary and the user adds guidance, the original text remains retrievable unchanged. A subsequent attempt links to the exact guidance version it used; no generated plan silently replaces a user constraint. |
| FR-009 | Council must persist the user's autonomous full-access preference at the chosen project or broader configured scope and apply it to subsequent authorized work without repeated confirmation. The effective policy must be visible before and during execution. | After selecting the policy once, ordinary permitted implementation, inspection and verification stages proceed without asking the same permission again. Reopening the project retains the policy; an explicitly narrower task override is honored. |
| FR-010 | Execution policy must describe actual harness capabilities and limits truthfully. A full-access preference must not be represented as bypassing a provider, managed installation or OS restriction. | If a required operation is unsupported or denied, Council reports the blocked capability and retained evidence. It does not show the check as passed, silently change global settings or claim a universal sandbox. |
| FR-011 | Council must validate supplied task data and resolve the execution destination before side effects. It must identify contradictions or missing prerequisites that prevent a safe, meaningful attempt. | Invalid structured input or an unavailable destination starts no agent. A task that names incompatible current and obsolete phase constraints is surfaced for correction rather than silently choosing which original constraint to discard. |
| FR-012 | The selected workflow must include only the stages needed by the task's uncertainty, consequences and acceptance criteria. A routine task must not require council voting, debate, planning-model calls or independent review when deterministic checks suffice. | A trivial bounded edit with a sufficient check can complete without extra model consultations. A consequential change requiring independent review includes that stage, with its reason visible in the plan and call budget. |

## 3. Route economically and use idle subscriptions

| ID | Requirement | Observable acceptance |
| --- | --- | --- |
| FR-013 | Automatic selection must prefer the least costly suitably capable configured target under the user's quality, account and payment preferences. Routine selection must not itself require a model call. | Given a validated small target and a larger target that both satisfy a routine task's requirements, the configured economy policy selects the small target and records the capability and cost-policy reasons. A more demanding task can choose a different target for a stated suitability reason. |
| FR-014 | Routing must distinguish Council-managed occupancy, reported external occupancy, allowance availability and unknown information. Council inactivity alone must never establish that an account is idle or has allowance. | With no external observation, an unused-by-Council subscription is shown as externally unknown. A user-reported busy Codex account and available Claude account remain distinguishable from that unknown state. |
| FR-015 | Under the configured policy, suitable idle subscription capacity must be usable without disrupting the programmer's current agent conversation. Capacity shared by several targets must not be counted multiple times. | While personal Codex is marked busy, a suitable available Claude subscription receives a background task. Launching that task neither changes the model in the existing Codex conversation nor creates a second allowance for a Claude model alias sharing the same account. |
| FR-016 | Occupancy, allowance and reference prices must retain source, observation time and relevant validity. Unknown, exhausted and expired information must remain distinct, and a reset time passing must not fabricate replenishment. | An expired positive report becomes unknown. An observed zero is not cleared by a price edit or the clock passing a reset. The UI identifies which observation supports a routing decision. |
| FR-017 | Automatic routing, retries and model escalation must remain within the declared task policy and budget. A larger model or more expensive workflow may be selected only when that policy permits it, and the reason must be recorded. | A failed economy attempt does not silently trigger an unbounded chain of larger models. When an allowed escalation follows a concrete failed check or ambiguity, its target and remaining budget are visible; a disallowed escalation leaves an actionable blocked outcome. |
| FR-018 | An explicit user account, harness or model pin must be honored. Failure of that choice must not silently substitute another account, provider, model or payment mode. | A pinned unavailable model produces a specific unavailable/blocked result or waits under the configured policy. It does not consume a different provider's allowance while reporting the original choice. |
| FR-019 | Council must not select or configure a Council-managed paid API execution path unless the provider/account and an applicable budget policy have been configured for that usage. A subscription's unavailable or unknown allowance must not imply consent to paid-credit fallback. | With only a subscription target configured, exhaustion does not cause Council to select or configure a paid API alternative. With a configured API target and permitted budget, selection records that payment path. Externally configured harness/provider overage and unknown provider-side usage are disclosed as outside Council's enforceable spending guarantees. |
| FR-020 | Usage and cost views must distinguish reported actual usage, explicitly labelled estimates, reference prices and unknown values. Council must not invent tokens, quota decrements, charges or savings from call counts or model names. | A harness that reports no tokens shows unknown token use, not zero. A reference price is not displayed as a measured charge. Multi-call workflows report their actual known receipts without claiming a percentage saving unsupported by a comparison. |

## 4. Coordinate implementation, review and verification

| ID | Requirement | Observable acceptance |
| --- | --- | --- |
| FR-021 | Council must produce an executable workflow connecting the task outcome to necessary implementation, review, deterministic verification and integration stages. The next required action and its owner must remain clear. | When an author finishes but review has not run, the task shows review pending rather than accepted. After review corrections, the board identifies the affected check or integration step as the next action. |
| FR-022 | Independent review, when required, must inspect the actual change and relevant acceptance evidence with suitable authorized access. Review results must identify what was inspected, concrete findings and unperformed checks. | A reviewer that could not open required source or run a necessary check cannot approve that missing review/check merely by returning a completed response. Its gap remains linked to the task and available for a compatible verifier or reviewer. |
| FR-023 | Blocking findings must lead to explicit correction work in the same task/change lineage. The workflow must recheck the affected acceptance conditions after correction without repeating unrelated stages automatically. | A reproduced validation defect is fixed, its regression check reruns and the finding's resolution links to that result. The prior author's artifact and review remain available, and unrelated successful tasks are not replayed. |
| FR-024 | Deterministic checks must record the exact checked change or source state, command/check identity, terminal outcome and relevant output. Agent statements about having run checks must be distinguishable from observed verifier evidence. | A check failure blocks acceptance when that check is required. A later source edit makes earlier check evidence historical until the relevant checks run against the changed result. A claimed check with no observed receipt remains unverified. |
| FR-025 | Multi-task workflows must execute independent work concurrently within configured capacity and honor explicit dependencies. Failed or unverified prerequisites must block dependent admission while admitted sibling work settles. | For two independent tasks and a third depending on both, the first two can overlap; the third starts only when the required predecessor outcomes are available. Failure of one does not erase the other's retained result. |
| FR-026 | Task handoffs must identify the accepted predecessor change/base and make required evidence available within the follower's actual access capabilities. A separate artifact path or prose report must not imply that predecessor changes are present in the follower's workspace. | A dependent implementation uses the intended predecessor files or records a specific integration/access blocker. A review of one author's change cannot accidentally inspect only the unchanged original checkout. |

## 5. Supply focused context and preserve complete evidence

| ID | Requirement | Observable acceptance |
| --- | --- | --- |
| FR-027 | Council must assemble scoped context and retrieve task-relevant source/evidence rather than repeatedly sending the entire project or every transcript. Context selection must preserve every applicable original constraint and acceptance condition. | A focused edit receives its relevant source and requirements without unrelated full histories. Retrieval and planning never delete a user constraint from the retained task or silently omit it from applicable execution guidance. |
| FR-028 | Generated summaries and compressed context must be identified as derived material, retain provenance and permit retrieval of the original. Insufficient context capacity must be handled explicitly rather than silently clipping acceptance-critical evidence. | A worker can obtain the cited original evidence behind a summary. If the selected target cannot fit required material, Council narrows/retrieves, uses permitted escalation or reports a context blocker; it does not report completion based on a silently truncated requirement. |
| FR-029 | Full task, attempt, review, verifier and change evidence must remain retrievable with stable linked identities. Routine views may show labelled previews but must not replace retained evidence with those previews. | A task card links to the complete recorded result and checks. Long records can be read through explicit bounded pages/sections without clipping the stored original or skipping unread entries. |
| FR-030 | Only the context relevant and authorized for a receiving stage may be propagated. Internal coordination, task data and agent messages must not create new authorization or automatically broadcast separately scoped content. | A peer's suggestion cannot change the task's payment policy or publication authority. A stage receives the evidence required for its work without unrelated conversations being copied into every prompt. |
| FR-031 | Normal progress, waiting, history and evidence inspection must not invoke an agent model. Observation must use compact bounded metadata by default, with explicit complete reads when needed. | Leaving the board open or waiting for a queued task adds no model calls. A user can inspect full results and refresh history without restarting work; large projects do not require full-transcript scans for each status update. |

## 6. Control execution and recover retained work

| ID | Requirement | Observable acceptance |
| --- | --- | --- |
| FR-032 | Lifecycle states must distinguish queued, active, paused, blocked, accepted/completed, failed and cancelled meanings as applicable. A transport response, wait timeout or partial result must not imply successful task acceptance. | A wait timeout leaves the attempt running and identifies it. A provider failure with partial edits remains failed/incomplete. UI, CLI and MCP present the same underlying task and attempt outcomes. |
| FR-033 | Pause must stop new workflow admission and retain a resumable checkpoint while already admitted work settles. Stop/cancel must request termination of admitted work, preserve evidence and expose ongoing cleanup honestly. | Pausing a task graph prevents the next dependent launch while active work drains. Resuming continues the saved unfinished work without replaying completed changes. Cancelled work is not shown as immediately quiescent solely because cancellation was requested. |
| FR-034 | New guidance and policy changes must apply at defined boundaries. New stages must recheck the current task instructions, ownership, cancellation, budget and account controls before dispatch. | Guidance changed during one active attempt is retained, and subsequent admission cannot use the obsolete plan unnoticed. Work already dispatched remains attributable to its original instruction version; Stop is available when it should not continue. |
| FR-035 | Restart and recovery must reconcile task ownership, known outcomes and retained changes before starting replacement work. Neither stale progress alone nor a missing response may authorize automatic replay of writes. | After a controlled owner crash, the next session shows interrupted work and retained artifacts, identifies completed identities and does not run the same edit again. A deliberately requested replacement attempt links to its predecessor. |
| FR-036 | Coordination must enforce declared shared capacity across concurrent Council hosts and preserve accepted cancellation and primary failures against late success. Uncertain process cleanup or unrecovered persistence faults must prevent conflicting new dispatch. | Two hosts cannot each independently consume the full shared limit. A late success response cannot clear an earlier accepted cancel or observed primary fault. An unknown-cleanup incident presents inspection steps rather than starting overlapping replacement writes. |
| FR-037 | Cancellation, shutdown and recovery must settle admitted evidence and owned processes, report unresolved cleanup explicitly and avoid destructive automatic repair. Durable operations must not replay model calls to recover from persistence failures. | A shutdown retains already returned sibling results while closing dispatch after an evidence fault. A failed cleanup leaves an actionable retained state; it does not delete unrelated paths, erase the original error or rerun the agent to reconstruct evidence. |

## 7. Protect existing work and deliver the accepted change

| ID | Requirement | Observable acceptance |
| --- | --- | --- |
| FR-038 | Council must preserve the programmer's dirty work, selected branch and unrelated files. It must isolate concurrent writers or otherwise provide explicit non-conflicting ownership and record the base and intended change destination. | Starting two writing tasks leaves pre-existing uncommitted edits intact. Their outputs have distinct attributable change identities. A target/base conflict is reported before overwriting user work. |
| FR-039 | The chosen workflow must integrate a verified result into the agreed task destination when the saved execution policy authorizes integration. Otherwise it must deliver an immediately reviewable change with the precise remaining action. | An authorized autonomous workflow applies the verified result to its selected destination and records the resulting identity. A review-only policy retains the result for acceptance. Neither workflow labels an unapplied patch as integrated. |
| FR-040 | Integration must verify that required evidence applies to the change being accepted and handle destination changes or conflicts explicitly. Failed integration must retain both the useful candidate and the original user work. | If the destination changes after verification, Council revalidates the affected integration or reports a conflict; it does not silently overwrite the new state. A resolved candidate remains traceable to its checks and source base. |
| FR-041 | External publication, deployment and other externally visible delivery must be included in the explicit task scope before execution. Existing authorization within that scope must be reused rather than repeatedly requested. | A task authorizing local implementation does not publish a package or deploy. A task explicitly authorizing the named deployment can proceed under its saved policy and records the external result or failure. |
| FR-042 | Council must provide documented evidence export, project-state backup/recovery and reviewed artifact cleanup with clear scope. Cleanup must preserve unaccepted or subsequently changed work unless its disposal is explicitly authorized. | Exported evidence identifies included data and excluded project/artifact material. Restoring a verified backup does not silently resume writes. Cleanup of one task cannot remove another task's files or discard later user edits as though they had been reviewed. |

## 8. Present one coherent product and qualify the release

| ID | Requirement | Observable acceptance |
| --- | --- | --- |
| FR-043 | The local UI must prioritize the project/task composer and `Auto` choices, followed by available agents, progress, evidence and usage. It must use the exact approved EjupiLabs brand assets, visual references and icon conventions. | The default task path has no mandatory voting/member/transport form. Visual acceptance compares real rendered screens with the approved EjupiLabs references; replacement logos or unrelated icon sets are not presented as the requested brand. |
| FR-044 | Newly authored product UI, functional documentation and setup/error guidance must be English, concise and actionable. Original task/source/evidence content must remain verbatim when fidelity requires it. | Loading, empty, blocked and failed states explain what happened and the next action. Keyboard operation, focus, accessible control names and retry states are verified in the actual interface. Original code or user evidence is not translated or rewritten merely to match UI language. |
| FR-045 | CLI, MCP and local UI must expose the same core project/task, routing, execution, waiting, evidence and control semantics. The programmer must not need to maintain a second external phase plan to understand Council's actual next step. | A task created through one interface is inspectable and controllable through the others with the same identity and outcome. MCP output remains protocol-valid; CLI machine-readable results separate diagnostics. |
| FR-046 | UI and API operations must tolerate stale reads, lost acknowledgements and repeated submission without duplicate work or silent overwrite. Existing drafts, selection and loaded evidence must remain intact when an unrelated update arrives. | A repeated start after a lost response returns the existing operation or a conflict instead of launching another attempt. A late detail response cannot repaint a newer selection or erase a draft; a failed read offers a retry of the intended query. |
| FR-047 | The release must provide deterministic offline tests for the complete useful programmer journey, documented supported platforms and separately reported authorized live adapter qualification. Claims must match actual terminal evidence. | The release test covers fresh setup, two configured targets, suitable idle-account selection, implementation/review/correction as needed, deterministic checks, authorized integration and restart/evidence inspection. Fake calls are labelled; unavailable CI runners and unperformed live tests are not counted as passes. |
| FR-048 | Each delivered feature must be traceable through the requested Specify workflow: specification, design/plan, dependency-ordered tasks, implementation, independent review, correction and acceptance evidence. Legacy feature count is not a release gate. | Feature delivery records reference these FR IDs, identify the actual check/review outcomes and contain no unresolved blocking finding at acceptance. A feature is not declared complete only because implementation tasks were ticked or old source was copied. |

## First-release exclusions

The first release is a useful development orchestrator with the five named harness adapters and local UI, CLI and MCP entrypoints. It does not require recreating weighted parliamentary votes, six equally prominent mode selectors, a universal model leaderboard, multiple independent inbox systems, recursive agent organizations or the legacy storage/API layout.

Those features may be added when an accepted use case warrants their cost. Their absence must not weaken the required routing, task execution, verification, full evidence, autonomy, dirty-work preservation, integration or recovery behaviors above. This document makes no promise of universal provider telemetry, provider-enforced spending caps, a universal OS sandbox, remote multi-user hosting or a particular implementation technology.
