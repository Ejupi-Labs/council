# Scoped retention operations

Status: **deferred research for the mandatory next feature**. This is not an active
or approved feature 007 contract. The retained draft below covers RCR-011–020 and
the retention parts of RCR-021–025 as originally proposed; it is neither an assertion
that these operations exist nor a substitute for the next feature’s specification,
independent review and approved design. API paths below are relative to `/api/v1`;
the CLI and UI address the same local owner and operation records.

## Common rules

IDs are existing opaque 32-hex values; revisions, byte counts and ordinals are
canonical decimal strings. Requests are strict typed objects, without unknown
fields. Each mutation has a `requestId`; the persisted fingerprint includes its
operation, exact scope, selection, destination, review and authority. Identical
replays return the recorded outcome or current unresolved operation before new
effects are considered. Reuse with different input is a conflict. A lost reply
is not permission to publish, restore or remove a second time.

Every operation has a durable `operationId`, `kind`, `state`, `source`, exact
scope, creation time and explicit next action. States are `preparing`, `ready`,
`applying`, `complete`, `incomplete`, `failed` or `uncertain`. A complete result
means every selected required member was captured and verified, or every selected
cleanup item was disposed of as authorized. Partial or uncertain effects never
mean complete. Reads and previews perform zero model calls. Private physical
identities and handles are controller facts and are not client-supplied proofs.

The server may return an asynchronous accepted operation; callers inspect its
status rather than treating an HTTP acknowledgement as completion. For every
effect, persist an exact intent before the OS operation and its observed result
afterward. An uncertain commit or outcome retains an incident and fences
conflicting work. No retry automatically repeats an uncertain filesystem effect.

## Selection and credential boundary

The selection preview identifies the selected project or task, each supported
record and artifact category, exclusions, inaccessible references, capture status
and destination. It distinguishes the Council project-state records and referenced
artifacts from the user's live project filesystem. Feature 007 does not recursively
copy an arbitrary working tree, vendor authentication directory, legacy state,
owner lock/descriptor, SQLite database or its WAL/SHM. Their omission is stated
in the manifest and UI/CLI; the backup does not claim to restore them.

Credential safety is determined **before reading selected bytes**, using only
trusted origin and typed-field provenance already established by Council. Eligible
generated metadata is limited to the explicit schema of Council-generated IDs,
enums, numeric fields, timestamps, record relationships and generated integrity
values. Do not treat arbitrary human text, harness output, paths, executable
arguments, project files or an artifact as safe solely because it is present in
Council storage, has an allowed filename, or is selected by a user. Provenance
must establish that its exact value or bytes were generated by a controlled,
credential-free source; a client-supplied flag or user assertion cannot establish
that fact. There is no inspection, scanning, copying or hashing of known vendor
credentials in either operation. Unknown provenance is an exclusion with a clear
reason; when selected required material cannot be established safe, the operation
fails closed or is `incomplete`, never a complete export or verified backup.

The positive acceptance fixture uses two projects and multiple artifacts made
entirely by the controlled fake fixture generator, which records trusted,
non-client-writable provenance for each exact generated field and artifact. The
selected project's required original input, records and artifact bytes are
synthetic known noncredential values with that provenance. Select all supported
readable members in that project and verify that all selected members appear,
the unrelated project's members do not, and restore makes the selected records
and identities available. This demonstrates a real scoped round trip, not a
runtime assertion that arbitrary user data is credential-free. A second fixture
uses a referenced vendor-credential path and an opaque member of unknown origin:
instrumented fake access verifies neither is opened; report the exclusions and
do not mark a required incomplete selection complete. Never use real credentials.

## Export and backup

| Operation | HTTP | CLI |
| --- | --- | --- |
| Preview task or project evidence | `POST /retention/exports/preview` | `retention export-preview --scope task\|project --id ID --destination PATH` |
| Export the captured preview | `POST /retention/exports` | `retention export --preview ID --request-id ID` |
| Preview project backup | `POST /retention/backups/preview` | `retention backup-preview --project ID --destination PATH` |
| Create backup from captured preview | `POST /retention/backups` | `retention backup --preview ID --request-id ID` |
| Inspect either operation | `GET /retention/operations/ID` | `retention inspect ID` |

Preview bodies contain `requestId`, `scope` (`{kind,id}`) and an explicit local
`destination`. Backup scope is a project; export scope is one task or one project.
Capture bodies contain `requestId`, `previewId` and `previewRevision`. A preview
captures the supported selection, exclusions and exact destination. An older or
changed selection is rejected, never silently refreshed. Destination is a local
absolute path, explicitly selected for this operation; do not overwrite an
existing file or grant external publication. The UI displays scope and privacy
before creation. Stored results expose a user-readable destination and manifest
identity, not private controller paths or process handles.

Build a project-scoped consistent logical snapshot, including the selected
records' referential closure, from one SQLite read transaction. Do not copy the
whole shared database. Freeze IDs, revisions, artifact identities, size and known
digests; copy only permitted, closed, complete members through controlled
identity-checked reads and verify the bytes actually copied. Revalidate the
selection and relevant revisions before publication. An active stream, changed
member, missing dependency, incompatible shared reference, permission error or
unavailable source produces an explicit incomplete result rather than a
verified complete backup. Do not claim an atomic snapshot across mutable SQLite
and filesystem objects solely from a database transaction.

A versioned portable manifest lists format and schema compatibility, source and
selection, logical record identities, dependencies, ordered member names, exact
sizes and SHA-256 digests, provenance class, included categories, exclusions and
unavailable references. Project filesystem inclusion is explicitly `omitted` in
this supported profile. The manifest never includes private owner tokens or
physical identity strings. Export is review evidence; only a complete backup
with its full selected referential closure is eligible for restore. Use bounded
members and total sizes, publish a private staged file only with an exclusive
no-replace effect after verification, and record actual durability limitations.
Hashing proves integrity of captured bytes, not that content is safe to share.

## Metadata-only history bundle and import

This separate profile provides a useful production path for existing projects
whose opaque content has no trusted credential-free provenance. It is an
**incomplete history bundle**, not a complete project backup, evidence export
or verified restore. Successfully writing or importing the bundle completes that
specific operation; the history's `completeness` remains `incomplete` everywhere.
It is never accepted by the complete-backup restore endpoint.

| Operation | HTTP | CLI |
| --- | --- | --- |
| Preview metadata history | `POST /retention/histories/preview` | `retention history-preview --project ID --destination PATH` |
| Create the captured bundle | `POST /retention/histories` | `retention history-create --preview ID --request-id ID` |
| Preview history import | `POST /retention/history-imports/preview` | `retention history-import-preview --bundle PATH --destination PATH` |
| Import the captured preview | `POST /retention/history-imports` | `retention history-import --preview ID --request-id ID` |
| Inspect either operation | `GET /retention/operations/ID` | `retention inspect ID` |

History preview takes `requestId`, `projectId` and absolute local `destination`;
creation takes `requestId`, `previewId` and `previewRevision`. Import preview
takes `requestId`, `bundlePath` and absolute local `destination`; import takes
`requestId`, `previewId` and `previewRevision`. The preview shows the exact
project identity, allowed field categories, excluded categories and local
destination. The resulting versioned manifest contains `profile` =
`metadata_history`, `completeness` = `incomplete`, the source project ID, the
supported schema/version, source snapshot revision, selected generated records,
and explicit omissions. It identifies missing task text, guidance, source and
project files, artifact payloads, opaque metadata, credentials, shared account
details, owner/process state and all execution/delivery authority. Neither UI nor
CLI may summarize the import as a full recovery or verified project backup.

Build the history only from an explicit typed allowlist of separately stored,
validated Council-generated fields. For the accepted v6 baseline this includes
project/task/attempt IDs and their relationships, task revision/state revision,
attempt revision and validated phase, and graph IDs/root relationships/version,
control/state revisions and validated state, where available as dedicated columns.
Artifact ID, owning attempt and recorded byte count may be listed as a metadata
reference with payload `unavailable`; it is not evidence that current payload
bytes exist or match. Exclude project paths, labels, arbitrary logical keys and
all `data`, `authority_data`, request, environment and output fields. Read only
the allowlisted columns in a project-scoped SQLite read transaction; never fetch
and decode a whole JSON record merely to extract a safe-looking field. Validate
ID formats, enum domains, counts and relationships before emission. If any field
cannot be established as Council-generated and safe without inspecting excluded
content, omit it and record its category/reason. Do not open, read, hash or scan
artifact payloads, project files, vendor credentials or unselected projects.

Freeze the selected history IDs/revisions and compare relevant source revisions
before publication. A changed or unreadable selection is an incomplete or failed
operation; never quietly create a mixed-point-in-time history. Use the same
bounded archive, manifest integrity checks, exclusive publication, no-overwrite,
durable request receipts and uncertainty rules as the other retention operations.
Metadata is still private information and is not represented as anonymized.

Import verifies profile, version, integrity, limits, strict field schemas,
relationships, source identity, destination containment and collision freedom
before any effect; rejects links, unsafe names, duplicates and extra fields. It
rechecks the exact opened bundle and selected absent destination at commit, then
journals any filesystem effect and atomically records a read-only imported-history
projection in its own isolated namespace. It does not create executable task,
attempt, workflow, graph, receipt, capacity, owner or policy records, nor attach
to a live project by matching a source ID. It retains source IDs as historical
references and clearly marks all omitted data `unavailable`. Source phase/state
values are historical observations, never current execution or accepted-outcome
proof. An imported history cannot dispatch, resume, retry, publish, rebind or
authorize cleanup, even when its source IDs match existing entities. Its UI and
CLI are inspection-only and have no model calls. Same-request replay and uncertain
import effects follow the common operation rules; unproven effects stay fenced.

Acceptance uses an existing-project fixture whose normal user-provided fields and
artifact payloads are present but not examined. Export/import a history using the
dedicated columns, confirm logical relationships and incompleteness labels through
UI and CLI, and assert payload opens, model calls, automatic dispatches and changes
to the live project's records are all zero. Test an unknown enum, changed snapshot,
corrupt/tampered bundle, malformed or injected field, path/link attack, ID
collision, interruption, and lost acknowledgement. This fixture is independent
of and cannot substitute for the complete-backup round trip or its trusted
provenance requirement.

## Verified restore

| Operation | HTTP | CLI |
| --- | --- | --- |
| Verify and preview | `POST /retention/restores/preview` | `retention restore-preview --backup PATH --destination PATH` |
| Restore captured preview | `POST /retention/restores` | `retention restore --preview ID --request-id ID` |
| Inspect outcome | `GET /retention/operations/ID` | `retention inspect ID` |

Preview takes `requestId`, `backupPath`, and `destination`; restore takes
`requestId`, `previewId`, and `previewRevision`. The supported destination is a
new, absent Council-owned project restore directory or empty namespace under an
explicitly identified local root. It must not replace a live state database,
merge with an existing project, overwrite user files, or silently import into a
different project. If the original logical IDs collide in the target namespace,
reject; never silently renumber or overwrite them. Import preserves logical
identities and provenance, but re-creates private files and records their newly
observed physical identities. A verified backup is not an authorization to
resume old owners, tasks, model calls or external publication.

Before any destination effect, validate the complete archive and manifest,
version, declared members and dependencies, duplicate names/IDs, limits,
integrity, source identity and destination conflict. Reject absolute, parent,
drive-qualified, alternate-stream, aliased, symlink, hard-link and other unsafe
member paths. Check current policy and owner, then revalidate the same opened
backup and destination identities at the commit boundary. Stage into exclusively
created private space; use an atomic relational import with validated references
and an exclusive destination publication where supported. There is no assumption
that database and filesystem effects share one atomic transaction: persist each
intent/result and fence on interrupted or ambiguous effects. A rejected pre-effect
restore leaves source and destination unchanged; a partial restore reports known
and uncertain effects and exposes reconciliation without replay. Restored work
with uncertain ownership remains interrupted and fenced until reconciled.

## Reviewed artifact cleanup

| Operation | HTTP | CLI |
| --- | --- | --- |
| Preview task cleanup | `POST /retention/cleanups/preview` | `retention cleanup-preview --task ID` |
| Dispose captured selection | `POST /retention/cleanups` | `retention cleanup --preview ID --items ID[,ID...] --request-id ID` |
| Inspect outcome | `GET /retention/operations/ID` | `retention inspect ID` |

Preview takes `requestId` and `taskId` and performs no deletion. It returns a
stable review ID/revision and exact Council-owned artifact IDs, categories,
current state, acceptance/retention status and exclusions. A cleanup request
contains `requestId`, `previewId`, `previewRevision`, an explicit subset of
`artifactIds`, and `disposalAuthority` for each unaccepted or changed item. The
authority is captured for that exact current identity and state by a fresh review;
it cannot be inferred from general full access or an older broad selection.

Before each removal, recheck task ownership, reference use, review revision,
physical identity, type, link status, exact bytes/digest and current authority.
Shared or still-required evidence is excluded. Do not recursively delete a
worktree or follow symlinks. Hold a native directory/parent handle and use an
exclusive move into Council-owned quarantine followed by verification of the
actual moved object; a prechecked pathname alone is not identity proof. Retain a
swapped/unverifiable item and any quarantine object as uncertain. Record intent,
verified quarantine and removal outcomes, including sync limitations. A missing,
changed, inaccessible or uncertain item is reported per item; no item is
silently relabelled deleted. Preserve accepted task/graph/review/delivery records,
the review, explicit authority, and audit trail after disposal.

## Required evidence

Tests must cover the positive synthetic round trip above, two-project isolation,
unknown provenance and vendor-path exclusion, selected artifact and source drift,
incomplete streams, partial read/write and lost acknowledgement. Restore cases
include corruption, incompatible format, duplicate/traversal/link entries, size
limits, changed destination, ID collision, interruption at each durable boundary,
and zero automatic admissions. Cleanup cases include two tasks, a changed item,
fresh exact authority, unrelated files, symlink/hard-link and name-swap races,
partial removal, uncertain acknowledgement and retained audit records. Execute
actual UI and CLI operations against the same owner, including retry and stale
selection, and qualify supported native platforms without a live provider.
