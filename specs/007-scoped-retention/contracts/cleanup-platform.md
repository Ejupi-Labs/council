# Draft Contract: Platform-Safe Reviewed Cleanup

**Status: research and implementation contract, not a claim of implemented cleanup.** This feature must satisfy the scoped review, exact authority, unrelated-work preservation and effect-journal requirements in `spec.md`. The credential-safe payload eligibility policy remains unresolved. Cleanup approval does not authorize credential inspection or establish that an item is credential-free.

## Scope and threat model

Cleanup begins with an explicit task-scoped, bounded preview of individually identified Council-owned candidates and dependencies. The subsequent request identifies the exact reviewed items and captured revision; unselected, shared, still-required, inaccessible, changed, unresolved, unverified and unrelated objects are retained. Changed or unaccepted work needs a fresh exact review and explicit authority in addition to all ownership and dependency checks. A directory selection is not authority to recursively remove unknown or unreviewed descendants.

Assume external processes or the user can modify a name, file, parent directory, link, destination or project after preview and during cleanup, including from the same user account. The Council owner lock serializes Council's own state; it does not freeze the user's filesystem or prevent another same-user process from writing to it. A stale preview, previously captured name, inode/file ID alone or absence of a Council claim is not proof of current exclusive ownership. Each potentially destructive effect needs a durable intent and exact authority, fresh object and parent checks, and a known or explicitly uncertain outcome. Repeated requests, restart and acknowledgement loss must not repeat an effect.

No content of unknown or ineligible provenance may be read, copied or hashed. In particular, do not use a content read to decide whether a candidate contains credentials. The user's pending answer must resolve whether observing metadata or moving a possible credential counts as prohibited inspection or disposal; until a policy supports an operation, exclude uncertain candidates before that operation. If bytes are eligible for comparison, their provenance and exact authority must already be established. A user cleanup selection does not establish either. Recorded artifact hashes establish integrity only; they do not certify absence of credentials.

## Reusable implementation primitives and gaps

Current `internal/workspace` application primitives demonstrate useful security properties, but are private, effect-specific building blocks, not a supported cleanup API:

- `applyOpenDirectory` / `applyOpenRelative` retain parent and object handles and use no-follow traversal; `applyNativeInfo` checks ordinary object kind, physical identity and platform metadata. Existing implementations reject hard-linked regular files and unsupported metadata. A cleanup implementation needs its own reviewed-item and owner checks, bounded inventory and carefully limited access rights.
- `applyRenameExclusive` moves a checked object to a non-overwriting quarantine name. A successful quarantine is a **move**, not deletion, space reclamation, secure erasure or proof that every link or copy disappeared. Store the quarantine disposition and exact identity; leave retained objects inspectable by authorized means.
- The existing application controller in `apply_execute.go` may read a displaced object's bytes and store them as an artifact after a source-name race. Cleanup must not reuse that branch: a competing object may be unrelated or contain credentials. Do not open its contents, copy it, hash it or delete it. Preserve whatever is safely retained, record the actual namespace change and uncertainty, and fence any conflict that cannot be resolved.
- Existing application helpers do not implement a generic verified cleanup deletion. A new implementation must prove the exact object removed at the effect boundary on every supported platform. Do not claim an unlink-by-name is equivalent to deletion of the previously opened object, or that recording an uncertainty retroactively preserves an unrelated path that was already displaced.

## Linux and macOS

`apply_native_unix.go` traverses anchored directories with `openat` and `O_NOFOLLOW`, accepts only ordinary single-link files, checks retained descriptor versus directory entry, and requires source and destination on the same supported mounted filesystem. Linux's `renameat2(RENAME_NOREPLACE)` and Darwin's `renameatx_np(RENAME_EXCL)` provide exclusive destination naming (`apply_native_linux.go`, `apply_native_darwin.go`). Unsupported filesystems, mount identity, permissions, metadata, or cross-device moves fail closed. Unix directory `fsync` is attempted by the existing primitive; its availability and successful return must be observed, not assumed.

**Source-name race:** these rename operations identify the source by parent descriptor and name, not by the previously validated file descriptor. A name can be swapped after the last check and before rename. A post-rename identity check can discover that a different object was moved, but cannot guarantee the unrelated path was never displaced. The required preservation of unrelated paths therefore needs an independently established exclusion of such concurrent namespace mutation, or another positively verified platform primitive/protocol; a plain check-then-rename plus an uncertainty record is insufficient to claim that stronger guarantee. When exclusion cannot be established, retain/refuse the candidate. If a competing object is nevertheless found in quarantine after an effect, do not inspect its bytes or delete it; report and preserve the actual observed state.

**Deletion race:** ordinary `unlinkat(parent, name)` is likewise name-based; checking a held FD and then unlinking the name alone can remove a replacement. A merely private-looking directory, random name or Council lock does not by itself exclude same-user namespace edits. No current Unix cleanup primitive proves exact-object deletion under this threat model. The implementation must establish a defensible exclusive namespace/protocol or retain/refuse the item. If it cannot prove a requested permanent deletion, report the limitation rather than calling a quarantine move or uncertain unlink `deleted`.

## Windows

`apply_native_windows.go` opens relative children with `NtCreateFile`, `OBJ_DONT_REPARSE` and reparse-point checks, validates single-link files and holds the object handle. Its `FileRenameInformation` operation is based on the retained source handle and a retained target-directory handle. Unsupported attributes, streams, extended attributes, security descriptors, labels or access/sharing conditions are rejected. Those constraints are not proof of authority over a candidate, exclusive control of its descendants, or credential-safe content.

Sharing/access restrictions can prevent opening or moving a file safely; return retained or unsupported rather than broadening access or removing a replacement. Existing retained root handles and third-party handles can deny DELETE sharing. A handle-bound deletion/disposition operation is not implemented by the current cleanup code and requires new, independently tested Windows-specific behavior and exact post-effect observation. Test on native Windows, including open-handle and sharing conflicts.

The current `applySyncDirectory` explicitly lacks a supported Windows directory-flush guarantee. Record the platform's actual namespace durability as unavailable where applicable; do not claim an atomic or power-loss-durable namespace transaction merely because a file handle or database receipt was flushed. Unknown effects after a crash remain inspectable and fenced until proven safe.

## Durable effects and results

For each selected object, persist the operation identity, reviewed object/parent identity, scoped authority, intended action and current guard before the effect. Afterward append its observed result: retained, rejected, moved to exact quarantine, deleted only when proven, failed before effect, or uncertain. Include any affected namespace and no-follow identity evidence without retaining sensitive content. A change between review and effect invalidates that item's authority; it cannot be silently accepted by another selected item's approval.

Quarantine and final deletion, if both supported, are separate reviewed effects with distinct outcomes and crash boundaries. Do not automatically delete a quarantined object on restart, infer an unrecorded effect from a missing source, or retry an uncertain effect. Protect unselected and shared artifacts and preserve all prior task, acceptance and audit records. The manifest/review cannot claim complete cleanup when any selected effect is unsupported, retained, unresolved or uncertain.

## Native acceptance scenarios

Use disposable roots and fake Council-owned objects, never user data or live providers. Execute the relevant OS-specific tests on native Linux, macOS and Windows; cross-compilation is not a substitute for observing filesystem behavior.

1. Create two tasks with independent owned files and a shared reference. Review a subset for one task; verify only eligible, unchanged, selected, unshared objects receive the specifically supported effect. Preserve the second task, the shared object, audit records and unrelated source/destination paths.
2. Replace a reviewed file or parent, change metadata or content after review, inject a new directory descendant, remove an item, or change sharing/dependency state. Require a fresh exact review and authority where permitted; no pre-existing authorization follows the replacement. Verify identity checks do not read unknown bytes.
3. Inject source-name swaps immediately before and after the final Unix name check, at rename, and before any deletion. Demonstrate that the chosen platform protocol prevents unrelated namespace changes; if prevention is unavailable, reject before effects. A post-rename mismatch must be retained and reported honestly, not treated as proof that no unrelated path changed.
4. Test symlinks, Windows junctions/reparse points, alternate streams, hard links, special files, mount boundaries, unsupported metadata/ACLs, pre-existing quarantine names and permission or Windows sharing failures. No fallback follows a redirect, overwrites a destination, traverses recursively or touches another task.
5. Crash or inject persistence failures before permit, after permit, immediately before/after quarantine, before/after any supported deletion and before acknowledgement. Restart, inspect and retry the exact request: no duplicate effect, no automatic unlink or reapplication, no false completion, and exact known/uncertain outcomes and conflict fences remain.
6. Instrument content access for ineligible and possible credential objects. Assert no prohibited read, copy or hash occurs, including error, quarantine-mismatch and restart paths. The selected interpretation of metadata and move restrictions must be tested explicitly once the user and eligibility design resolve it.
7. Verify platform-specific durability reporting against actual `fsync`/namespace support and Windows's qualified limitation; a simulated power-loss boundary may not be represented as stronger than the tested OS guarantee.

If the implementation cannot demonstrate exact safe effects under these conditions, expose only the operations it can prove and leave the stronger cleanup acceptance criterion open. Preserve user work rather than substituting a best-effort recursive delete.
